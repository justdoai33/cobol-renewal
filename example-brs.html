Business Rules Specification — Billing Deduplication

This is a real BRS produced by the framework from a production COBOL billing deduplication program. It demonstrates technology-agnostic EARS rules, traceable back to specific COBOL source lines and forward to implementation.

Section 1: Overview

The billing deduplication process compares the current day's cardholder billing records against the accumulated monthly billing security file. Its purpose is to prevent any cardholder billing record that has already been loaded to the downstream system from being loaded again. Each cardholder account must appear at most once in any given monthly billing load.

The process runs as part of the daily processing path only. On the first business day of a new month, the monthly security is empty (reset by the month-end path) and all records are treated as new.

This process runs twice per job execution: once for standard card accounts, and once for a secondary card brand. Both runs are functionally identical; they operate on separate streams of data.

Section 4: Business Rules

4.1 Processing Sequence

BR-001: The billing deduplication process SHALL process records in ascending account key sequence.

BR-002: The billing deduplication process SHALL process all records from both the monthly security file and the daily billing file before terminating.

4.2 Duplicate Detection

BR-003: WHEN an account key in the daily billing file matches an account key in the monthly security file, the system SHALL classify that daily billing record as a duplicate.

BR-004: WHEN a daily billing record is classified as a duplicate, the system SHALL write it to the duplicate rejection file.

BR-005: WHEN a daily billing record is classified as a duplicate, the system SHALL NOT write it to the updated billing security.

BR-006: The account key used for comparison SHALL be a 17-byte value comprising the company identifier, product code, and account number fields, located at bytes 3 through 19 of each record.

4.3 New Record Handling

BR-007: WHEN an account key exists in the daily billing file but does not exist in the monthly security file, the system SHALL classify that record as a new billing record.

BR-008: WHEN a daily billing record is classified as new, the system SHALL write it to the updated billing security.

4.4 Security File Passthrough

BR-009: PARTIAL WHEN an account key exists in the monthly security file but does not exist in the daily billing file, the system SHALL [determine correct disposition — see gap G-002].

4.5 Completion

BR-010: WHILE records remain unprocessed in either input file, the system SHALL continue processing.

BR-011: WHEN both input files are exhausted, the system SHALL close all files and terminate normally.

4.6 Empty File Handling

BR-012: IF the monthly security file is empty at the start of processing, the system SHALL treat all daily billing records as new records.

BR-013: PARTIAL IF the daily billing file is empty, the system SHALL [determine correct behaviour — see gap G-004].

4.7 Audit

BR-014: The system SHALL produce a duplicate rejection file on every execution, even if no duplicates are found (the file may be empty).

BR-015: The system SHALL produce an updated billing security file on every execution, even if no new records are found (the file may be empty).

Section 7: Error Handling

BR-016: IF a file I/O error occurs during processing, the system SHALL terminate with a non-zero exit code.

BR-017: PARTIAL IF a record is encountered with an unexpected length or format, the system SHALL [determine correct behaviour — see gap G-005].

Section 8: Constraints

BR-018: The billing deduplication process SHALL only run during the daily processing path (i.e., when the current processing month is the same as the previous processing month).

BR-019: The monthly security file and daily billing file SHALL both be sorted in ascending account key sequence before this process runs.

BR-020: The billing deduplication process SHALL be executed separately for standard card accounts and secondary brand accounts. The two streams SHALL NOT be mixed.
