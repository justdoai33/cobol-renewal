G-002: Security-Only Records — WRITE Commented Out

HIGH — affects output correctness

Affects: Core deduplication logic, BRS BR-009, FRS FR-006, TDD main branch

Question

In the original COBOL, the handling of the case where a record exists in the monthly security but has no matching record in today's billing file contains a commented-out WRITE statement:

IF W-COMPARE-MAST < W-COMPARE-CHG
   MOVE INMAST-REC TO OUTMAST-REC
*  DISPLAY 'LESS ' OUTMAST-REC(3:20)       ← commented debug display
*  WRITE OUTMAST-REC                        ← WRITE IS COMMENTED OUT
   PERFORM Z-READ-MAST
   GO TO B-EXIT.

The WRITE is commented out. This means records that are only in the security (not in today's billing) are NOT written to the output.

Two Interpretations

Interpretation A (output = new records only): The commented-out WRITE is intentional. Output only ever contains records from the daily file that are not yet in the security. The full security accumulation is handled by a separate downstream step that concatenates the previous security + today's new records.

Interpretation B (output = full updated security): The commented-out WRITE is a bug. Output should contain all records: prior security records (passed through) plus today's new records.

Evidence Supporting Interpretation A

  • A downstream concatenation step exists that explicitly builds the full security independently
  • The output file and the accumulated security file are different datasets
  • The downstream load system likely only needs today's new records on each run

Impact on Modernisation

This is the single highest-priority gap. If Interpretation A is correct, the implementation is straightforward. If B, we need to understand why the WRITE was removed and whether the current system is producing incorrect output.

Information Needed

  • Original developer or a business analyst who knows the downstream load requirements
  • What does the downstream process do with the output file? Does it expect all records for the month, or just today's new ones?

G-007: Equivalence Testing Strategy

HIGH — required before production deployment

Question

How will we prove that the modernised implementation produces identical output to the COBOL for the same input?

  1. Can we obtain a set of real (or representative) input files from production?
  2. Can we obtain the corresponding COBOL output files to compare against?
  3. Are there any known cases where the COBOL output is incorrect?
  4. What is the tolerance for differences — must output be byte-for-byte identical?

Impact: Without an equivalence testing strategy, we cannot confidently deploy the modernised system. This gap must be resolved before any production-readiness work begins.

G-004: Empty Daily Billing File Behaviour

Medium

Question

What should happen if the daily billing file is empty? The original COBOL does not explicitly handle this case. Should an empty daily file be treated as:

  • (a) Normal — output files are empty, job continues
  • (b) Warning — log and continue
  • (c) Error — abort the job

In production, has the daily file ever been empty?

G-008: File Versioning in Modernised System

Medium

Question

The original system uses GDG (Generation Data Group) semantics — each run creates a new generation and reads the current one. The modernised batch system needs an equivalent mechanism. Options:

  • (a) Date-stamped filenames
  • (b) A file management layer with "current" symlinks
  • (c) A database table tracking file versions
  • (d) Object storage with versioning (e.g. S3)

Decision depends on target infrastructure and downstream system requirements.
