Functional Requirements Specification — Billing Deduplication

The FRS bridges business rules and technical design. It defines system-level behaviour with full data mappings, exact byte offsets, and record layouts — enough detail for any developer to implement correctly.

Section 1: Overview

Component: billing-deduplication

Pipeline position: Receives merged, sorted billing records from the field merge stage. Produces the updated monthly billing security for downstream system loading.

Run context: Daily processing path only

Section 5: Functional Requirements

5.1 Pre-processing Validation

FR-001: The process SHALL open all input and output files before any record processing begins.

FR-002: The process SHALL perform an initial read of INMAST. IF INMAST is empty, the process SHALL log a diagnostic message and set MAST comparison key to HIGH-VALUES (so all incoming records are treated as new).

FR-003: The process SHALL perform an initial read of INCHG. IF INCHG is empty, the process SHALL set CHG comparison key to SPACES and continue.

5.2 Main Processing Loop

FR-004: The process SHALL repeat the comparison loop until both input files are exhausted (EOF on both files).

FR-005: On each iteration, the process SHALL compare the 17-byte key of the current security record against the 17-byte key of the current daily record.

Branch 1: Security key < Daily key

FR-006: WHEN the current security key is less than the current daily key, the process SHALL [see GAPS G-002 for correct disposition].

FR-007: After processing the security record, the process SHALL read the next record from the security file.

FR-008: IF the security file is exhausted, the process SHALL set the security key to HIGH-VALUES and set the EOF flag.

Branch 2: Security key > Daily key

FR-009: WHEN the current security key is greater than the current daily key, the process SHALL write the current daily record to the output security (new record — not yet in security).

FR-010: After processing the daily record, the process SHALL read the next record from the daily file.

FR-011: IF the daily file is exhausted, the process SHALL set the daily key to HIGH-VALUES and set the EOF flag.

Branch 3: Keys equal (duplicate)

FR-012: WHEN the current security key equals the current daily key, the process SHALL write the current daily record to the rejection file (duplicate).

FR-013: After processing a duplicate, the process SHALL read the next record from both input files.

5.3 Post-processing

FR-014: After the main loop exits, the process SHALL close all files.

FR-015: The process SHALL exit with return code 0 on successful completion.

Section 7: Error Handling & Edge Cases

Empty Security File (first day of month)

Legitimate at month-start. Sets security key to HIGH-VALUES so all daily records follow the "new record" branch.

Modernised system: Detect empty security at open time. If empty, write all daily records to output with no comparison needed.

Unsorted Input

The original COBOL does not validate sort order. If input files are not sorted, the comparison logic produces incorrect results silently.

Modernised system: Consider adding sort-order validation (detect if current key < previous key and raise an error).
